# План реализации: роли (админ / гость), защита пароля и деплой

Документ описывает, что и зачем сделано, как выложить проект, что осталось за рамками
и какие шаги логично предпринять дальше. Исходное ТЗ — `task.txt`.

## 1. Два уровня прав

При входе показывается окно «Выберите вашу роль» (модальное, закрыть нельзя без выбора):

- **Гость** — весь просмотр: проекты, доска задач, экран «Все задачи», отчёты и выгрузка
  XLSX, скачивание резервной копии. Без добавления, редактирования, удаления и таймера.
- **Администратор** — полный доступ. При выборе роли запрашивается пароль.

Выбранная роль запоминается в `localStorage` (ключ `tasktracker_role`), в шапке есть бейдж
роли и кнопка «Выйти».

## 2. Защита пароля администратора

Реализован первый уровень: **пароль не попадает в клиентский бандл**.

- Пароль передаётся на сервер и сверяется там: `scrypt` + `timingSafeEqual`.
- Хранится только scrypt-хеш, в переменной окружения `ADMIN_PASSWORD_HASH` — **без** префикса
  `VITE_`, поэтому значение доступно лишь серверу.
- Побочный эффект: в браузере пароль нельзя найти поиском по собранному JS. Проверяется
  командой `findstr /S /I /C:"ваш-пароль" dist\*` (не должно быть совпадений).
- Добавлен лимит попыток входа (10 за 15 минут на IP) и ответ `429` с `Retry-After`.

### Что важно понимать про модель безопасности

| Задача | Статус |
| --- | --- |
| Гость не может **узнать пароль** | решено — проверка на сервере |
| Гость не может **подделать роль** | не решено — роль хранится на клиенте |
| Гость не может **изменить данные** | не решено — данные в `localStorage` |

Роль остаётся клиентским флагом: её можно переключить через DevTools. Cookie-сессия этот
вопрос не закрывает, потому что данные всё равно лежат в браузере. Реальное разграничение
прав возможно только вместе с серверным хранением данных (раздел 5).

## 3. Отдельная тема: данные не разделяются между браузерами

Данные хранятся в `localStorage`, то есть **у каждого браузера своя копия**. Если открыть
боевой сайт на другом устройстве, гость увидит пустой список проектов, а не ваши задачи.

Как следствие:

- роль «Гость» осмысленна, когда просмотр идёт **в том же браузере**, где ведётся работа
  (например, вы показываете задачи на своём компьютере);
- для гостя на другом устройстве нужен бэкенд с общей базой данных (раздел 5) —
  альтернатива без сервера только одна: передать JSON-бэкап, но «Загрузить бэкап»
  у гостя отключён, и это лишь разовая копия без обновлений.

Это самый важный пункт для дальнейшего развития.

## 4. Деплой

Проект — статический SPA (`dist/`) плюс serverless-функция (`api/login.js`).
Целевая платформа — Vercel.

1. Сгенерировать хеш: `npm run hash-password -- "ваш пароль"`.
2. Добавить переменную `ADMIN_PASSWORD_HASH` в Settings → Environment Variables.
3. Задеплоить: `vercel` / `vercel --prod`, либо импортировать репозиторий в панели.
   Параметры сборки зафиксированы в `vercel.json` (framework `vite`, output `dist`).
4. Для SPA-роутинга `vercel.json` переписывает на `/index.html` все пути, **кроме** `/api/*` —
   иначе catch-all перекрыл бы функцию входа.
5. После смены пароля нужен redeploy.

**Публикация только `dist/` на статическом хостинге** приведёт к тому, что вход
администратора не будет работать (функция `api/login.js` не выполнится). Это осознанное
поведение «fail closed».

**Netlify** для этого варианта не подходит «как есть»: там нет `/api`-функций Vercel,
логику пришлось бы переносить на Netlify Functions, а catch-all в `_redirects` перекрыл бы
эндпоинт. Файл `public/_redirects` удалён, чтобы не создавать ложного впечатления поддержки.

## 5. Возможные улучшения (следующие итерации)

- **Бэкенд с общей базой данных — приоритет №1.** Решает сразу три задачи: гость видит
  реальные данные с любого устройства, права проверяются на сервере, роль нельзя подделать.
  Логичный стек: Vercel Functions + Postgres (Vercel Postgres / Neon / Supabase),
  тот же фронтенд переходит с `localStorage` на API. Уже готовый `/api/login` —
  фундамент для этого этапа.
- **Cookie-сессия** (подписанный HttpOnly-токен) — имеет смысл добавлять вместе с переходом
  на серверные данные, а не раньше.
- **Несколько администраторов**, смена и ротация пароля.
- **Отчёт сразу по всем проектам** с колонкой «Проект» и быстрыми пресетами периода.
- **Печать / PDF** отчёта (отдельные print-стили).
- **Журнал изменений** задач (кто и когда менял).
- **Версионирование схемы данных** `localStorage` и миграции при будущих изменениях.
- **Напоминание о резервной копии**: данные в браузере легко потерять при очистке кэша.
